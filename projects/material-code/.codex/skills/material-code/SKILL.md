# 清力物料编码

这是工程本地 Skill。使用本目录的 `scripts/workflow.py` 驱动同目录业务脚本，并依赖所在工程的
`pyproject.toml`、本机 SQLite 镜像和运行状态。底层脚本带入口门禁，直接执行会失败；所有业务操作
必须通过 `workflow.py`，由入口强制隔离 job、校验授权、备份写操作并保存活动状态。

## 安装形态

不要用 `skill-installer` 把本目录安装到全局 Skill 目录。拉取仓库的
`projects/material-code` 分项后，在该工程根目录运行：

```powershell
uv sync --locked
```

随后以工程根为工作目录启动或打开 Codex。`.codex/skills/material-code` 是唯一权威 Skill 实现；
不要复制 `.venv`、数据库、业务 Excel、`output` 或临时调试目录。迁移到新环境时重建依赖，并由
用户在本机重新提供或明确选择权威数据源。

## 运行约定

1. 工程根通过当前工作目录及父目录中的 `pyproject.toml` 动态定位；也可由用户显式设置
   `MATERIAL_CODE_ROOT`。代码中不得写死盘符或某台电脑的绝对路径。
2. 首次迁移到新电脑后运行 `uv sync --locked` 重建本机环境，不复制旧电脑的 `.venv`。使用项目环境运行：

   ```powershell
   uv run python ".\.codex\skills\material-code\scripts\workflow.py" <command>
   ```

3. 路径含中文或空格时始终单独传参，不拼成二次解释的命令字符串。
4. 需要核对编码规则、Excel 字段或数据权威关系时，读取
   [references/business-rules.md](references/business-rules.md)。
5. 权威总表很大时，只人工检查表头和少量抽样行；完整 Excel→SQL 导入必须交给
   `sync_db.py` 的流式 Python XML 解析，不把整张表加载进模型上下文。
6. 同步时只允许读取 Excel 的第一个工作表。第二页及后续工作表不读取单元格数据、
   不导入 SQL、不参与编码流水号计算。
7. 同步报告中，只把“产品名称非空且 A-K 全空”统计为本次待申请；J 为空但 A-K 已有内容的行
   单独报告为异常缺码，不与待申请混在一起。

## 不可放宽的脚本硬约束

以下规则必须由代码拒绝违规调用，不能只依靠提示词、文档或操作者自觉：

- 每份申请在 `prepare` 前必须消费一次有效的数据库来源确认；确认不可跨申请复用。
- `sync`、批量 Top1 和阈值自动处理必须带工作流确认参数；底层脚本禁止直接执行。
- 申请候选固定为 Top5，只查询 `retired=0` 的在用物料；CLI 不提供改变数量或纳入停用物料的参数。
- 权威总表同步固定只读取第一个工作表，且只有 J 非空的行进入正式 SQL。
- 申请 job 创建后，只要数据库文件指纹变化，`show`、`commit`、`top1`、`auto` 全部拒绝旧候选。
- 唯一精确匹配必须复用；多个精确匹配必须人工选择精确编码，任何批量命令不得代选。
- `prepare`、`show`、`commit`、`top1`、`auto` 均不得改变正式数据库；检测到变化必须恢复并失败。
- skill 不提供向正式数据库直接插入预定编码的函数或命令；正式数据库只能由 `sync` 全量重建。
- 子流程出现错误、跳过、无选择或部分成功标记时，工作流必须把整次写操作视为失败并恢复结果。

## 决策顺序

### 1. 先检查，再刚性询问数据库来源

每个新任务先运行：

```powershell
... workflow.py status
```

只要任务将处理一份新申请表，无论数据库是否存在、同步时间多新，都必须先把当前数据库的
源 Excel、同步时间和行数告诉用户，并明确询问二选一：

1. 提供新的权威总表并重新同步数据库；
2. 明确回复沿用当前数据库。

在用户明确选择前必须暂停申请处理，不得运行 `prepare`，不得把沉默、含糊答复、仅提供申请表，
或“继续处理”等表述推断为沿用当前库。

若用户明确回复沿用当前数据库，先记录一次性确认：

```powershell
... workflow.py use-existing --confirmed
```

若用户提供新总表并要求更新，运行：

```powershell
... workflow.py sync "<新权威总表.xlsx>" --confirmed
```

`use-existing` 成功或 `sync` 成功都会生成与当前数据库指纹绑定、仅供下一次 `prepare` 使用的
一次性确认记录。`prepare` 会刚性校验并消费该记录；缺少确认、确认已被上一份申请消费，或确认后
数据库发生变化时，入口必须拒绝执行。每份新申请都要重新询问和确认。

一旦用户改为提供新总表并开始 `sync`，此前尚未消费的“沿用现有数据库”确认立即失效；即使同步
失败并恢复了旧数据库，也必须重新询问用户，不能退回旧确认继续 `prepare`。

`status` 显示的源 Excel 或同步时间只用于帮助用户决策；不要据文件名日期擅自判断数据已过期，
也不要代替用户选择。

### 2. 默认逐项人工选择

用户给出申请表后运行：

```powershell
# 前提：用户已明确选择新总表同步或沿用现有库，并已产生一次性确认
... workflow.py prepare "<申请表.xlsx>"
... workflow.py show 1
```

`prepare` 解析并预计算候选，且先执行严格精确匹配；它不修改数据库，但可能把复用结果写入
本 job 的结果 Excel：

- 产品名称和产品规格与唯一一条在用物料完全一致：明确提醒用户原编码，直接把原编码及分类
  写入结果 Excel，并将整行以浅红底、深红字标记，便于人工核对复用记录；标记该项已处理并跳到下一项，绝不生成新编码。申请单位无论是否为空都按
  申请表原值写入；为空时保持为空，不沿用原物料单位。
- 名称和规格完全一致但对应多个不同在用编码：把全部精确匹配编码优先列入候选，不自动猜测；
  用户选中哪一个，就直接复用该旧编码，仍不生成新编码、不写数据库。
- 没有唯一精确匹配：向用户展示 `show` 的完整 Top5 表格，并要求回复候选 `1`–`5`；
  `0` 表示留空、不生成编码。

拿到明确选择后提交，再展示下一项：

```powershell
... workflow.py commit 1:2
... workflow.py show 2
```

严格遵守：

- “全部生成新编码”只表示要生成，不等于候选已选定。
- 不把一次含糊的全局答复解释成全部 Top1。
- 只有用户明确说“剩余/后续全部用 Top1”时，才运行：

  ```powershell
  ... workflow.py top1 --confirmed
  ```

- 只有用户主动指定自动阈值时，才运行：

  ```powershell
  ... workflow.py auto 0.7 --confirmed
  ```

不要在默认流程中额外询问是否开启阈值自动选择。

### 3. 写操作必须走入口

以下操作会生成申请结果或修改正式镜像：

- `prepare`：只为唯一精确匹配写入复用结果，不修改数据库。
- `use-existing --confirmed`：只在用户明确回复沿用当前库后，记录一次性数据库确认。
- `commit`：只提交用户已明确选择的项并写独立结果 Excel，不修改正式 SQL。
- `top1 --confirmed`：只在用户明确放行剩余 Top1 后生成预定编码，不修改正式 SQL。
- `auto <阈值> --confirmed`：只在用户明确要求阈值自动处理后生成预定编码，不修改正式 SQL。
- `sync <总表> --confirmed`：只在用户明确同意同步后执行。

入口会在写入前备份，并在子流程报错或部分跳过时恢复数据库与本 job 结果。不要绕过
`--confirmed`，不要直接修改 SQLite。

同步示例：

```powershell
... workflow.py sync "<用户提供的权威总表.xlsx>" --confirmed
```

同步成功会使旧 job 候选失效；重新对申请表执行 `prepare`。

## 失败处理

- 命令退出码非零：停止当前阶段，报告原始错误，不继续提交下一项。
- `prepare` 报告数据库来源尚未确认、确认已消费或数据库已变化：回到第一步询问用户；不得自行
  执行 `use-existing --confirmed`。
- `sync` 验证失败：入口会恢复同步前数据库；核对实际表头，再修正工程脚本映射。
- 申请流程若导致 `material_codes.db` 文件变化，工作流必须视为错误并恢复；正式库只能由
  权威总表同步产生。
- job 被同步标记为失效：重新 `prepare`，不要复用旧候选。
- 无候选：不要自行编造 C/E/G；向用户说明并请求分类依据或使用 `0` 留空。
- 唯一精确匹配项已经由 `prepare` 处理；不要再次询问候选或尝试提交新编码。
- 多个不同编码同时满足名称+规格完全一致时，必须把冲突编码交给用户，不能自动选最低、最高
  或最早编码；用户选择的必须是精确匹配编码，选择后直接复用而不是继续生成。

## 完成标准

完成申请时同时报告：

- 独立 job 结果 Excel 的绝对路径；
- 已复用已有编码、已生成、留空、待确认的项数；
- 每个新编码的 C/E/G 前缀、原最大编码和本次流水号；
- 新编码只是预定值，回填权威 ERP Excel 并重新同步后才正式生效。

导出数据库不是固定收尾步骤。只有用户要求或核对确有必要时才建议一次，不反复追问。
